# Move the script out, paint before parsing

SlickChart is slow to open mainly because the phone compiles about 3 MB of inline JavaScript on every launch, not because the network is slow or the app's own code is heavy. The measurements make this plain. On a 4x CPU-throttled phone profile over 4G, with a 300-client account and a Vercel-like server (brotli, ETag), a CPU profile spent **about 2.0 s in native "(program)" time** (HTML parse plus compiling the inline script) against **about 0.5 s across all of the app's own functions**. An experiment that changed one thing, moving the inline script into an external content-hashed `.js` file, brought repeat-launch "Home drawn" from **1.2–2.7 s to 0.57–0.63 s** and "all data" from **2.4–3.7 s to about 1.6 s**. First visit after a deploy improved from 2.5–2.8 s to about 2.0 s. That one change gets a returning provider under Apple's "first frame fast" goal and comfortably inside Google's 2 s repeat-load budget. Four smaller levers follow it. The 865 KB Tabler icon font from jsDelivr is bigger than the whole compressed app. The service worker is network-first and probably does not run at all inside the iOS Capacitor shell. Vercel's on-the-fly Brotli leaves about 28% of the HTML transfer on the table. The native splash hides on a fixed timer rather than on first paint. Each fix has to respect SlickChart's own constraint: old builds keep running against new servers until a provider relaunches, so hashed files must outlive the deploy that replaced them.

## Compiling 3 MB of inline script costs four times the app's own work

The profile result matches how V8 treats inline scripts, and the external-file experiment confirms it. V8 starts parsing a script on a background thread while it downloads ("streaming") once it has seen 30 kB, but **streaming explicitly excludes inline scripts**, which are parsed and compiled on the main thread. V8's guidance is to avoid inlining anything over about 1 kB ([v8.dev, The cost of JavaScript in 2019](https://v8.dev/blog/cost-of-javascript-2019)). Code caching is the bigger loss. On disk, an external script goes cold on first load, warm on the second (the cache is written), and hot from the third (compilation is skipped). An inline script's cache is instead attached to the HTML document and **holds only while the entire document is byte-identical**. A 200 response resets it to cold, while a 304 keeps it ([v8.dev, Code caching for JavaScript developers](https://v8.dev/blog/code-caching-for-devs)). SlickChart deploys often and every deploy changes the HTML, so the whole 3 MB starts cold again after each one. Device spread makes this worse on real phones: a Moto G4-class phone runs JavaScript 3–4x slower than a Pixel 3, and a low-end Alcatel 1X more than 6x slower ([v8.dev](https://v8.dev/blog/cost-of-javascript-2019)). The 4x lab profile is therefore a mid-range phone, not a worst case.

The size of the experiment's gain (roughly 0.6–2.1 s off Home on repeat launch) is larger than any other lever in this report. It also has the lowest risk of any structural change, because it needs no code splitting. The HTML keeps its markup and CSS and loads one classic `<script src="/js/app.<hash>.js">`, served `Cache-Control: public, max-age=31536000, immutable`, which is Vercel's own recommendation for content-hashed assets ([Vercel Cache-Control](https://vercel.com/docs/caching/cache-control-headers)). Two refinements push it further. First, split rarely changing code (large default libraries, templates, admin and recovery tools) from the frequently edited core. V8 invalidates a whole file's cache when any byte changes, so a fix to the notes screen should not cold-start the code that never moves. Second, precache the script in the service worker's `install` event. V8 gives scripts cached there a **"full", eagerly compiled code cache immediately**, provided they are classic UTF-8 scripts rather than ES modules ([v8.dev](https://v8.dev/blog/code-caching-for-devs)), which targets the first-launch-after-deploy number that improved least in the experiment (about 2.0 s). Chrome 136's Explicit Compile Hints (`//# allFunctionsCalledOnLoad` at the top of a file) cut foreground parse/compile by an average of **630 ms** across 20 popular pages ([v8.dev, Explicit Compile Hints](https://v8.dev/blog/explicit-compile-hints)). It applies to a small boot-critical file, not the whole bundle, because eager compilation costs memory.

iOS is the open question. JavaScriptCore has its own bytecode cache ([WebKit JSScript.h](https://webkit.googlesource.com/WebKit/+/master/Source/JavaScriptCore/API/JSScript.h)), but no public documentation says whether WKWebView caches inline versus external scripts differently. The lab numbers are Chromium. The change is still the right call for iPhones, because an external file is at minimum not re-downloaded when only markup changes, but the iOS gain has to be measured on a device rather than assumed.

The risks are specific to this codebase. `build-demo.cjs`, `check-generated.cjs`, the `FEATURES.md` generator and the tenant-isolation sweep all read `slickchart.html` as one file, so they need the build to produce the split and the checks to read the source. More important, **CLAUDE.md §1a says a provider keeps running the old build until she relaunches**, and a second device may not relaunch for weeks. If a deploy removes `app.<oldhash>.js`, an old page that needs it again (a reload from the HTTP cache, a lazily loaded chunk) gets a 404. The safe pattern is to carry previous hashes forward in the output for several releases and to load every chunk the page needs at boot, not lazily, until that retention is proven. This is a change for the release train, never the daytime path.

## Boot work after compile should paint first and merge later

Once compile is off the critical path, the remaining 0.5 s of app work and the network pull decide when Home appears. A long task is anything over **50 ms** ([web.dev, Optimize long tasks](https://web.dev/articles/optimize-long-tasks)), and the experiment's longest task was still **172–319 ms**. The standard fix is to break boot into chunks that yield to the main thread. The catch for an iPhone-first app is that **Safari supports neither `scheduler.yield()` nor `requestIdleCallback` by default** ([web.dev](https://web.dev/articles/optimize-long-tasks); [caniuse](https://caniuse.com/requestidlecallback)). The yield helper has to feature-detect and fall back to `new Promise(r => setTimeout(r, 0))`, and nothing that must run on iOS can depend on idle callbacks. The order that follows from the budgets is session check, read only what Home needs, draw Home, yield, then the `/api/store` pull and merge, then one loader per yield, then repair passes and rarely used features. SlickChart already wraps each loader in `_reloadStep`, which is a natural yield point. Large data literals over about 10 kB parse about **1.7x faster as `JSON.parse('…')` strings** than as object literals ([v8.dev](https://v8.dev/blog/cost-of-javascript-2019)), and parsing a multi-megabyte stored value is itself a likely 60–120 ms task on a phone (an estimate from desktop `JSON.parse` throughput, not a measurement), so each large key should be parsed once and never just to draw a header.

The step beyond that is to paint before the script runs at all. The app-shell model renders cached UI on repeat visits and loads content afterwards ([Chrome for Developers, app shell](https://developer.chrome.com/docs/workbox/app-shell-model)). For a client-rendered app the equivalent is a stored HTML snapshot of the last Home screen, written into the page by a tiny inline `<head>` script before the big script loads, and kept non-interactive until boot finishes. That would put a recognisable Home on screen in a few hundred milliseconds even on a cold compile. In a multi-tenant app it is also a privacy surface. The snapshot holds client names, so it must be stamped with the owner, shown only when it matches the signed-in owner, and purged on logout alongside `_purgeOffloaded()`. Drawing early is a read, but anything the early draw saves is the boot write-back hazard CLAUDE.md §3 describes, so the snapshot path must not persist anything. No published measurement of snapshot restore exists for vanilla-JS apps, so this is the item to prototype and measure rather than assume.

## The cache layers each leave time unclaimed

### The service worker waits for the network and fights the update model

`sw.js` (cache `slickchart-v83`) is network-first for every same-origin GET except `/api/`, and calls `skipWaiting()` on install and `clients.claim()` on activate. Network-first is what Workbox recommends for frequently updated HTML, with a **3 s network timeout** by default ([workbox-recipes](https://developer.chrome.com/docs/workbox/modules/workbox-recipes)), but SlickChart's version has no timeout, so a weak cell signal can hold the launch as long as the request hangs. The faster fit for this app is stale-while-revalidate on the `/slickchart` navigation: serve the cached shell immediately and fetch the new one in the background for next time ([Workbox strategies](https://developer.chrome.com/docs/workbox/modules/workbox-strategies)). That is exactly the "new code at next launch" contract `_checkForNewBuild` already enforces. The trade-off is one extra launch of lag before new code arrives, which makes API backward compatibility (§1a) matter slightly longer. The cache should also be bypassed when the cached build falls below a minimum version the server publishes. This reverses the earlier UI/UX report's network-first suggestion, which that report flagged as an unsourced inference. The unconditional `skipWaiting()` should go too. Workbox advises skipping waiting only on a message after the user accepts an update, because a mix of old and new assets "can cause unexpected behavior" ([Handling service worker updates](https://developer.chrome.com/docs/workbox/handling-service-worker-updates)), and once scripts are separate files a mid-session takeover could serve new chunks to an old page. The rule never to cache `/api/` stays as it is, because it protects tenant data.

### The iOS native shell almost certainly has no service worker

`capacitor.config.json` loads `server.url: https://slickchart.app/slickchart` with `limitsNavigationsToAppBoundDomains: false`, and `Info.plist` has no `WKAppBoundDomains`. WKWebView exposes service workers only to App-Bound Domains (up to 10, with the navigation limit turned on) or to default-browser apps ([WebKit, App-Bound Domains](https://webkit.org/blog/10882/app-bound-domains/); [Apple forums 773539](https://developer.apple.com/forums/thread/773539)). **On iOS native the app therefore relies only on HTTP revalidation**, which costs one round trip (Vercel answered a conditional request with a 0-byte 304 in testing) plus a full 823 KB download after each deploy. Capacitor's own docs say `server.url` "is not intended for use in production" ([Capacitor config](https://capacitorjs.com/docs/config)). Enabling App-Bound Domains needs a native rebuild, blocks navigation to unlisted domains (Square and Google OAuth would have to open in the system browser), and is reported to break plugins that inject JavaScript ([WebKit bug 227589](https://bugs.webkit.org/show_bug.cgi?id=227589)). The more robust long-term option is a small local loader in `native-shell` that boots the last good build from device storage and fetches the new one for next launch. That is a larger project. The cheap first step is a self-check line reporting whether `navigator.serviceWorker.controller` exists on each device, which turns this inference into a fact. Android WebView supports service workers, and Capacitor 7+ routes their requests through the bridge by default ([Capacitor config](https://capacitorjs.com/docs/config)), so the strategy change helps Android, Android Chrome and iOS home-screen PWA users directly.

### Compression and the icon font are pure transfer waste

Vercel serves Brotli automatically ([Vercel compression](https://vercel.com/docs/how-vercel-cdn-works/compression)), but the live `slickchart.html` body was **823,499 B**, essentially the gzip size, while Brotli q11 compresses the same file to **590,223 B**. About 28% of the download after each deploy is unclaimed, roughly 0.37 s on a 5 Mbps link. Vercel does not document its Brotli level or whether it serves precompressed `.br` files for static output, so the route to q11 is unconfirmed. Splitting the script out already limits the damage, since only changed files re-download.

The Tabler icon font is the largest single delivery cost found. `slickchart.html` line 18 loads a render-blocking cross-origin stylesheet from jsDelivr (39 KB) that pulls **`tabler-icons.woff2` at 864,648 B**, larger than the whole compressed app, for about **272 `ti-*` class names** the app uses. A shared CDN no longer buys a cache hit from other sites, because Chrome partitions the HTTP cache by top-level site ([Chrome, HTTP cache partitioning](https://developer.chrome.com/blog/http-cache-partitioning)). The service worker skips cross-origin requests, so on iOS native the font rides only the HTTP cache. web.dev's advice is direct: removing unused glyphs "can significantly reduce the filesize", and where possible icon fonts should be replaced with SVGs, which also cause fewer layout shifts and are more accessible ([web.dev font best practices](https://web.dev/articles/font-best-practices)). The practical move is a build-time subset by codepoint (pyftsubset or glyphhanger; [Walter Ebert](https://walterebert.com/blog/subsetting-web-fonts)), self-hosted on `slickchart.app` with a hashed name and `immutable`, with only the used `.ti-*` rules inlined. At full-set density (about 5,900 icons in 865 KB) that suggests roughly 30–60 KB, an estimate to confirm by running the subset. The risk is a missing icon when someone adds a new class, which a CI check that greps `ti-*` names against the subset removes. The SRI `integrity` attribute must be dropped or regenerated with the move. Use `font-display: block` for icons so fallback glyphs never flash.

### The client companion page is never cached at all

The client PWA is served by `api/client-page.js`, a function that embeds the 551 KB `slickchart-client.html` and sets **`Cache-Control: no-store`**, so every open by a client downloads and compiles the full page with no revalidation and no code cache. Per-token responses legitimately must not be shared across clients, so the same external-script pattern applies here: keep the per-request HTML small and `no-store`, and move the static JavaScript and CSS to hashed `immutable` files that carry nothing client-specific. Clients open the page rarely, so their launches are mostly cold; the gain is bytes and compile on every visit rather than warm-cache wins.

## A splash that waits on a timer wastes the fastest launches

Human limits set the targets. About **0.1 s** feels instant, about **1 s** keeps the user's flow, and beyond 1 s the UI should show it is working ([NN/g, Response Times](https://www.nngroup.com/articles/response-times-3-important-limits/)). Apple's WWDC19 guidance targets the **first frame within 400 ms**, of which about 300 ms belongs to the app, and explicitly allows placeholders for data that arrives later ([WWDC19 session 423](https://developer.apple.com/videos/play/wwdc2019/423/)). RAIL puts repeat-visit load **under 2 s** ([web.dev, RAIL](https://web.dev/articles/rail)). A provider opening the installed app every morning is a repeat launch, so the honest goal is Home with real (cached) content under 1 s and taps answered within 100–200 ms. With the external script, Home at 0.57–0.63 s meets the first part. The app's own `performance` marks, not a stopwatch, should confirm that on Ashley's devices.

The native layer can squander that gain. SlickChart's `package.json` has no `@capacitor/splash-screen` plugin, and the app never calls `SplashScreen.hide()`, so the launch screen hands off whenever the web view first paints, and WKWebView's default background is white ([WebKit bug 215479](https://bugs.webkit.org/show_bug.cgi?id=215479)). If the plugin is added, its defaults (`launchAutoHide: true`, `launchShowDuration` 500 ms) add a fixed delay. Capacitor's docs recommend `launchAutoHide: false` and calling `SplashScreen.hide()` "as soon as the app is ready" ([Capacitor SplashScreen](https://capacitorjs.com/docs/apis/splash-screen)). For SlickChart "ready" means Home's first paint from local data, inside a `requestAnimationFrame` after the draw, never after the cloud pull. The white flash is fixed natively, by setting the LaunchScreen storyboard background to the app's first-paint colour; changing only the plugin's `backgroundColor` changes the flash's colour without removing it ([Ionic forum](https://forum.ionicframework.com/t/background-flickering-on-startup/188364)). The page should set `html, body` to the same colour in inline CSS before any script. Apple's HIG adds that the launch screen should resemble the first screen and carry no text or branding ([Apple HIG, Launching](https://developer.apple.com/design/human-interface-guidelines/launching)). Android 12+ uses the system SplashScreen API, and a legacy custom splash adds startup time ([Android, App startup time](https://developer.android.com/topic/performance/vitals/launch-time)).

Perceived speed after the first frame comes from never blocking on the network. Cached content should appear at once and refresh quietly, the stale-while-revalidate pattern applied to data ([web.dev](https://web.dev/articles/stale-while-revalidate)). When nothing is cached, a skeleton that mirrors the real layout beats a spinner for full-screen waits under 10 s, and **waits under 1 s need no indicator at all**, since a flashed placeholder feels jarring ([NN/g, Skeleton Screens](https://www.nngroup.com/articles/skeleton-screens/)). The earlier UI/UX report's rule still holds: "No clients" must never render while data is loading. For tap speed, Lighthouse warns above **800 DOM nodes** and errors above **1,400** ([web.dev, DOM size](https://web.dev/articles/dom-size-and-interactivity)), and a 300-client list passes that quickly. `content-visibility: auto` with `contain-intrinsic-size` cut rendering from **232 ms to 30 ms** in web.dev's demo and is supported from **Safari 18** ([web.dev, content-visibility](https://web.dev/articles/content-visibility)), so it is a cheap win on current iPhones and a no-op on older ones.

## Recommendations ranked by gain per unit of risk

| # | Change | Expected impact | Main risk | Path |
|---|---|---|---|---|
| 1 | Move inline JS to one external content-hashed classic script, `immutable`; keep old hashes deployed for several releases | Measured: repeat Home 1.2–2.7 s → ~0.6 s; all data 2.4–3.7 s → ~1.6 s; post-deploy Home 2.5–2.8 s → ~2.0 s | Build and checks assume one file; an old open build 404s if its hash is removed | Train |
| 2 | Subset and self-host the Tabler font (or switch to SVG), drop the jsDelivr CSS | Removes ~865 KB plus a cross-origin render-blocking request; subset est. 30–60 KB | Missing icons when new classes are added; needs a CI grep | Train |
| 3 | Add boot `performance.mark`s to the self-check (script start, top-level done, hydrate done, Home painted, `/api/store` done, merge done, repairs done) and a "service worker controlling: yes/no" line | Turns every later decision into a measurement from Ashley's own phone | None | Train |
| 4 | Yield between boot phases with a `setTimeout` fallback; draw Home before the pull; one `_reloadStep` per chunk | Cuts the 172–319 ms longest task toward 50 ms; taps answer during boot | Boot write-back guards (§3) must hold | Train |
| 5 | SW: stale-while-revalidate for the shell, precache scripts at `install`, message-driven `skipWaiting`, minimum-build override | Removes the launch round trip and the bad-signal hang; full code cache after a deploy on Chromium | One extra launch before new code; API compatibility must last a release longer | Train |
| 6 | Splash: storyboard and `html,body` colour match; if the plugin is added, `launchAutoHide:false` and hide on first paint | Removes the white flash and any fixed splash delay | Native rebuild and store review | Native release |
| 7 | Client page: small `no-store` HTML plus hashed static JS/CSS | Clients stop re-downloading ~550 KB per open | Same old-hash retention as #1 | Train |
| 8 | Split rarely changing code into its own file; later, lazy-load admin, builders and reports | Most deploys leave most of the code cache hot | Lazy chunks are exactly what 404s on old builds | Train, after #1 has run a while |
| 9 | Snapshot paint of last Home, owner-stamped, purged on logout | Home visible before any script runs, even cold | Shows another provider's names if the owner stamp or purge is wrong | Train, after a privacy review |
| 10 | iOS: local loader in `native-shell` or App-Bound Domains | Real offline-capable cache on iOS native | OAuth and plugin breakage; App Store submission | Separate project |

Measurement needs both lab and field. In the lab, the existing Playwright Chromium setup with CDP CPU throttling at 4x and 6x approximates mid and low phones (the 3–6x device spread is from [v8.dev](https://v8.dev/blog/cost-of-javascript-2019); the mapping to throttle rates is common practice, not a calibration), run twice per build to see cold and hot code cache. V8's `v8.compile` trace slices show whether a cache was produced or consumed ([v8.dev](https://v8.dev/blog/code-caching-for-devs)). Long Animation Frames give per-script attribution, including `sourceCharPosition` inside an inline monolith ([Chrome, LoAF](https://developer.chrome.com/docs/web-platform/long-animation-frames)), and Lighthouse fails "JavaScript execution time" above **3.5 s** ([Chrome, bootup-time](https://developer.chrome.com/docs/lighthouse/performance/bootup-time)). None of that exists in Safari or WKWebView, which expose neither LoAF nor INP, so the `performance.mark` numbers printed in the self-check are the only reliable iPhone field data. Splitting the marks into "Home painted" and "fully usable" mirrors Android's TTID/TTFD split ([Android, App startup time](https://developer.android.com/topic/performance/vitals/launch-time)) and shows whether a slow launch is late paint or late data.

## Conclusion

The profile changes where the effort should go. The instinct for a slow PWA is to chase bytes and network, but here the network is already cheap on repeat launch (a 304 costs nothing), and the phone was spending four times as long compiling the app as running it. That makes the single-file architecture itself, not any feature, the performance bottleneck, and it means the gain compounds with deploy frequency: the more often SlickChart ships, the more launches start cold under the inline model, and the fewer would under hashed files. The release train and the "old build keeps running" rule are what make this safe to adopt, because they already force the retention and compatibility discipline that hashed assets require.

Three things remain unknown and decide the next round. iOS JavaScriptCore caching of external versus inline scripts is undocumented, so the iPhone gain from #1 must be read off a real device's marks. Whether the service worker runs in the iOS shell is an inference until the self-check reports it. The icon-font subset size is an estimate until the subset is built. Each takes minutes to settle, and settling them first keeps the larger projects (a local iOS loader, code splitting, snapshot paint) from being built on a guess.
