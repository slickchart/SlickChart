# Audit the app against 60 testable rules

The current standard for a mobile-first PWA that a solo esthetician uses mid-treatment, and that her clients open from a magic link, is **WCAG 2.2 Level AA as the hard floor, with Apple's and Google's platform figures as the "should" tier above it**. Almost every part of that standard reduces to a number a headless browser can measure: **24×24 CSS px targets (fail) and 44–48 px (warn)**, **4.5:1 text and 3:1 UI contrast**, **16 px minimum on form fields** so iOS Safari does not zoom, **no `user-scalable=no` or `maximum-scale` below 2**, **no horizontal scroll at 320 px**, **LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1**, **under ~800 DOM nodes per screen**, and **toasts that stay at least 4 s and never carry the only copy of something important**. The parts that cannot be reduced to pixels matter most for a health-adjacent, multi-tenant product: an empty list must never render while data is still loading, offline edits must show "saved, will sync", deletes need undo or a confirmation that names the item, and booking, intake and portal pages must load **no third-party analytics or ad pixels**, because FTC and Washington MHMDA enforcement reaches aesthetic providers whether or not HIPAA applies. Below, the rules are tiered P0 (fails WCAG AA, risks data trust, or creates legal exposure), P1 (platform guidance or strong usability evidence) and P2 (polish). Each rule has a detection method suitable for Playwright plus axe-core against the local `slickchart.html` and `slickchart-client.html`. Where a figure rests on practitioner sources rather than a primary specification, the report says so.

## WCAG 2.2 AA sets the floor and the platforms sit 20 px above it

WCAG 2.2 is the current W3C Recommendation, dated 12 December 2024, and its new criteria are the ones a CRUD app most often fails ([WCAG 2.2](https://www.w3.org/TR/WCAG22/)). WCAG 3 is still a Working Draft as of March 2026. APCA was removed from it in 2023, and the WCAG 3 contrast method was still undecided in April 2026, so **APCA is not a substitute for 4.5:1** in an audit ([W3C](https://www.w3.org/WAI/news/2026-03-03/wcag3); [Adrian Roselli](https://adrianroselli.com/2026/04/wcag3-contrast-as-of-april-2026.html)).

The target-size rule shows how far apart the tiers are. **SC 2.5.8 (AA) requires 24×24 CSS px**. An undersized target can still pass on spacing if a 24 px circle centred on it does not intersect another target or another undersized target's circle, and inline links inside sentences are exempt ([Understanding 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)). Apple's HIG asks for a **44×44 pt hit region** on iOS, with **28×28 pt as the absolute minimum** ([Apple HIG Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons); [Apple HIG Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). Google asks for **48×48 dp separated by 8 dp**, roughly 9 mm of finger ([Android Accessibility Help](https://support.google.com/accessibility/android/answer/7101858?hl=en)). A provider tapping with gloved or wet hands needs the platform figure, not the legal one. The audit should therefore fail at 24 px and warn at 44/48 px, with in-session controls (start note, camera, save, next client) held to 48 px. On a device-width viewport, one CSS px equals one iOS pt and one Android dp. That equivalence is standard practice but is not stated in any of the sources.

Contrast follows the same pattern. **SC 1.4.3 requires 4.5:1 for text and 3:1 for large text**, where large means at least 24 CSS px, or at least 18.66 px bold. The relative-luminance formula uses the 0.04045 linearisation threshold. Setting a text colour without a background colour is itself flagged, so `body` needs an explicit background ([WCAG 2.2](https://www.w3.org/TR/WCAG22/)). **SC 1.4.11 requires 3:1 for control boundaries, state indicators and focus rings** against adjacent colours, measured from CSS values and never rounded ("2.999:1 fails") ([Understanding 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)). Apple goes further for dark mode and asks app makers to "strive for 7:1" on custom colour pairs in small text ([Apple HIG Dark Mode](https://developer.apple.com/design/human-interface-guidelines/dark-mode)). Material recommends **#121212 rather than pure black** for dark surfaces, with desaturated accents ([Material dark theme](https://m2.material.io/design/color/dark-theme.html)). That figure comes from the Material 2 page; the Material 3 tonal-surface equivalent could not be checked.

Focus has two AA criteria. **2.4.7** requires a visible indicator. **2.4.11** fails when a sticky header, bottom tab bar or toast covers the focused element entirely, and `scroll-padding` is the documented fix ([Understanding 2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)). The AAA criterion 2.4.13 is a good engineering target: an indicator covering at least a 2 px perimeter (4w + 4h px²) that changes by at least 3:1 between states ([Understanding 2.4.13](https://www.w3.org/WAI/WCAG22/Understanding/focus-appearance.html)).

Four criteria added in 2.2 apply directly to SlickChart. **2.5.7 Dragging Movements (AA)** requires a single-tap alternative for every drag, including reorder, swipe-to-delete and drag-to-reschedule. **3.3.8 Accessible Authentication (AA)** forbids blocking paste or password managers; magic links and pasteable one-time codes satisfy it. **3.3.7 Redundant Entry (A)** forbids asking for the same information twice in one flow. **3.2.6 Consistent Help (A)** requires help or contact links to sit in the same relative order on every screen ([WCAG 2.2](https://www.w3.org/TR/WCAG22/)).

## Typography and iOS input zoom hinge on 16 and 17 pixels

WCAG sets no minimum font size, so the numbers come from Apple. iOS body text defaults to **17 pt on 22 pt leading** (a ratio of about 1.29), footnotes are 13 pt, and **11 pt is the floor for any text** ([Apple HIG Typography](https://developer.apple.com/design/human-interface-guidelines/typography)). Apple also asks that text be enlargeable to **at least 200%**, the same figure as SC 1.4.4 ([Apple HIG Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). The commonly quoted Material 3 body sizes (bodyLarge 16/24, bodyMedium 14/20) were not verified at the source. The 16 px rule for web body text is therefore an inference that both platforms support, not a quotation.

The most often missed mobile-web rule has no Apple documentation behind it, but practitioners agree on it: **iOS Safari zooms the page when a focused field's rendered text size is under 16 px**, and the page stays zoomed afterwards ([Rick Strahl](https://weblog.west-wind.com/posts/2023/Apr/17/Preventing-iOS-Textbox-Auto-Zooming-and-ViewPort-Sizing); [HeroUI #5326](https://github.com/heroui-inc/heroui/issues/5326)). Locking the viewport is the wrong fix. iOS 10+ ignores `user-scalable=no` by default, while Android Chrome and Firefox enforce `maximum-scale=1` and so block zoom for low-vision users ([MDN viewport](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/meta/name/viewport)). Use `font-size: max(16px, 1em)` on `input, select, textarea` instead. The audit must use the *rendered* size, so it has to account for `transform: scale()` ancestors and for fields inside modals that are created after boot.

## Honest feedback states stop "my data is gone" panic

For a product whose worst incidents have been providers believing their work was lost, interface states are a data-trust issue more than a polish issue. NN/g's thresholds are concrete. **Show no indicator under about 1 s**, because a looping animation that brief is distracting. **Show a spinner or skeleton for 2–10 s**. **Show percent-done with a time estimate beyond 10 s**, or a record count for batches ("Updating address 3 of 50") ([NN/g Progress Indicators](https://www.nngroup.com/articles/progress-indicators/)). Skeletons must mirror the real layout; a frame-only skeleton reads as broken ([NN/g Skeleton Screens](https://www.nngroup.com/articles/skeleton-screens/)). The empty-state rule matters most for SlickChart: an empty state has to distinguish loading from error from genuinely empty, teach what will appear, and offer a button to start. **"No records" must never show while content is still loading** ([NN/g Empty States](https://www.nngroup.com/articles/empty-state-interface-design/)). Salesforce and SAP agree: say what the area is for and why it is empty, keep the message to about one line, and hide filters on a full-page empty state ([Lightning](https://spring-20.lightningdesignsystem.com/guidelines/empty-state); [SAP Fiori](https://www.sap.com/design-system/fiori-design-web/v1-96/foundations/best-practices/global-patterns/designing-for-empty-states); [PatternFly](https://v5-archive.patternfly.org/components/empty-state/design-guidelines)).

On validation timing the sources genuinely disagree. NN/g and Baymard's large-scale testing favour validating when the user leaves a field, and clearing the error on each keystroke once it is fixed ([NN/g](https://www.nngroup.com/articles/errors-forms-design-guidelines/); [Baymard](https://baymard.com/blog/inline-form-validation)). GOV.UK says "do not validate when the user moves away from a field" and validates on submit, because its users include many slow typists and assistive-technology users ([GOV.UK Validation](https://design-system.service.gov.uk/patterns/validation/)). Both reject validating while the user is still typing the first time, and both put the message beside the field, keep everything the user typed, and avoid "invalid", "oops" and "please" ([GOV.UK Error message](https://design-system.service.gov.uk/components/error-message/)). For the client portal, where older clients fill in intake forms, the GOV.UK on-submit approach is the safer default. For provider forms either is defensible. The audit should enforce consistency within the app rather than pick a winner.

Toasts are where accessibility and data safety meet. Material-derived systems auto-dismiss snackbars after **4–10 s** (Flutter's default is 4 s, MUI's example 6 s) ([Flutter](https://api.flutter.dev/flutter/material/SnackBar/duration.html); [SAP Fiori snackbar](https://www.sap.com/design-system/fiori-design-android/v25-8/components/feedback/snackbar/usage)). The official Material 3 page could not be retrieved. Under **WCAG 2.2.1**, an auto-dismissing message is a time limit **unless the same information or function is available elsewhere** ([Understanding 2.2.1](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html)). So an Undo toast is acceptable only if a recently-deleted list also exists, and "photo not saved, tap to retry" must persist. NN/g's guidance on destructive actions is to **prefer undo over confirmation**, because routine confirmations train users to click through. Reserve confirmations for irreversible actions, name the item ("Delete Jane Doe?"), and label the buttons with outcomes ("Delete client" / "Keep client"), never Yes/OK ([NN/g Confirmation Dialogs](https://www.nngroup.com/articles/confirmation-dialog/)). Native `confirm()` cannot relabel its buttons, so every call to it fails this rule automatically. The dialog should open with focus on the least destructive action, trap Tab, close on Escape and return focus to the control that opened it ([ARIA APG Dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)).

|---|---|---|---|

| E2 | P0 | Errors keep input | Return 500, or go offline, on save; every field value is unchanged and a Retry is offered ([GOV.UK](https://design-system.service.gov.uk/components/error-message/)) |

## Bottom navigation, safe areas and motion tie the app to the device

A bottom navigation bar should hold **2–5 destinations** (3–5 is the traditional figure), with the active item always labelled. Above five, use a drawer, and on wider windows switch to a navigation rail ([SAP Fiori M3 nav bar](https://www.sap.com/design-system/fiori-design-android/v25-8/components/m3-standard-components/navigation-bar/usage); [Material bottom navigation](https://m1.material.io/components/bottom-navigation.html)). The popular thumb-zone diagram is weaker evidence than it looks. Hoober's 1,333 observations found **49% one-handed use**, but in a 2017 correction he said people tap the screen centre more, and more accurately, than the reach diagrams implied ([UXmatters](https://www.uxmatters.com/mt/archives/2013/02/how-do-users-really-hold-mobile-devices.php)). The defensible rule is narrow: keep destructive and low-priority actions out of the upper-left and away from frequent actions. Do not move everything to the bottom edge.

Edge-to-edge layout needs `viewport-fit=cover` plus `env(safe-area-inset-*)` padding on every fixed header and footer, for example `padding-bottom: calc(1em + env(safe-area-inset-bottom))` ([MDN env()](https://developer.mozilla.org/en-US/docs/Web/CSS/env); [web.dev Learn PWA](https://web.dev/learn/pwa/app-design)). A plain **`100vh` overflows** under Safari's dynamic toolbar. Use `svh` or `dvh` (Safari 15.4+) ([web.dev viewport units](https://web.dev/blog/viewport-units)). The 300 ms tap delay disappeared years ago on any page with `width=device-width` (iOS 9.3, Chrome 32), so `touch-action: manipulation` is now only optional insurance ([Chrome for Developers](https://developer.chrome.com/blog/300ms-tap-delay-gone-away); [MDN touch-action](https://developer.mozilla.org/en-US/docs/Web/CSS/touch-action)). `overscroll-behavior-y: contain` suppresses the browser's pull-to-refresh, and `user-select: none` belongs on UI chrome only, never on note text ([web.dev Learn PWA](https://web.dev/learn/pwa/app-design)).

Dark mode needs more than inverted colours. Set `color-scheme: light dark` so native controls and scrollbars match. Provide two `theme-color` metas with `media="(prefers-color-scheme: …)"`, using solid colours only ([MDN theme-color](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/meta/name/theme-color)). Inside Capacitor, the native StatusBar plugin sets the bar colour, not `theme-color`; that is an inference that was not checked against Capacitor's docs. Reduced motion maps directly to iOS Settings > Accessibility > Motion and Android's "Remove animations", and has been Baseline since January 2020 ([MDN prefers-reduced-motion](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)). Under `reduce`, Apple asks for fades in place of scaling, zooming and sliding ([Apple HIG Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). JavaScript-driven `scrollIntoView({behavior:'smooth'})` and `element.animate` calls must check `matchMedia` themselves, because CSS media queries do not reach them.

## A 2 MB single file needs boot-time budgets, not byte budgets

The Core Web Vitals thresholds are unchanged for 2025–2026. "Good" is **LCP ≤ 2.5 s, INP ≤ 200 ms and CLS ≤ 0.1**; "poor" is above 4 s, 500 ms and 0.25. All three are judged at the 75th percentile ([web.dev thresholds](https://web.dev/articles/defining-core-web-vitals-thresholds)). INP replaced FID in 2024 and counts every tap, from input through processing to the next paint ([web.dev INP](https://web.dev/articles/inp)). Any task over **50 ms** is a long task. The recommended fix, `scheduler.yield()`, **is not supported in Safari**, so a `setTimeout` fallback is mandatory for an iPhone-first app ([web.dev long tasks](https://web.dev/articles/optimize-long-tasks)). Long Animation Frames give script-level attribution in Chromium only ([Chrome LoAF](https://developer.chrome.com/docs/web-platform/long-animation-frames)). That leaves a real gap: neither iOS Safari nor the Capacitor WKWebView exposes INP or LoAF, so responsiveness on iPhone can only be approximated, by timing handlers with `performance.now()` around `requestAnimationFrame`.

Lighthouse 13 (October 2025) changed what an automated audit can rely on. **`dom-size` became an insight**, the image and font audits merged into insights, and **`offscreen-images` was removed with no replacement**, so lazy-loading now has to be checked by the audit itself ([Chrome blog: Lighthouse 13](https://developer.chrome.com/blog/lighthouse-13-0)). The official DOM-size figures remain a **warning at about 800 body nodes and an error at about 1,400** ([Chrome docs](https://developer.chrome.com/docs/lighthouse/performance/dom-size)). For a single-file app that keeps every screen's markup in the document, hidden screens count toward that number. The CLS rules are each automatable: width and height, or `aspect-ratio`, on every image and video; space reserved for late-injected content; banners that overlay rather than push; and animation of `transform` and `opacity` only ([web.dev CLS](https://web.dev/articles/optimize-cls)).

| ID | Tier | Rule | Threshold / test |
|---|---|---|---|
| P1 | P1 | Lab vitals | Lighthouse mobile: LCP ≤2500 ms, CLS ≤0.1, TBT as the INP proxy |
| P2 | P1 | Interaction latency | `web-vitals` `onINP` ≤200 ms with 4× CPU throttling on scripted taps (open client, save note, switch tab) |
| P3 | P1 | Long tasks | PerformanceObserver `longtask`: record the boot task length; no task >50 ms per scripted tap; log the worst LoAF and its `sourceURL` |
| P4 | P1 | DOM size | `querySelectorAll('*').length` per screen: warn >800, fail >1,400 |
| P5 | P1 | Media sizing | Every `img`/`video` has width and height or a computed `aspect-ratio` |
| P6 | P2 | Lazy images | Below-the-fold images `loading="lazy"`; the LCP image is not lazy |
| P7 | P2 | Animated properties | Transitions and animations limited to `transform` and `opacity` |
| P8 | P2 | Fonts | Every `@font-face` sets `font-display`; Google Fonts URLs include `&display=` |
| P9 | P1 | iOS yielding | Long loops yield with a `setTimeout` fallback, because `scheduler.yield` is absent in Safari |

## Offline, storage and installs behave differently on iOS 26

Storage on iOS is a cache, not a vault. Since Safari 17, an origin may use **up to 60% of disk in a browser app but only 15% in other apps**, and eviction is best-effort and least-recently-used, unless `navigator.storage.persist()` is granted ([WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/)). Capacitor's own documentation warns that iOS may reclaim WebView localStorage, "and the same can be said for IndexedDB" ([Capacitor storage](https://capacitorjs.com/docs/guides/storage)). Safari's 7-day deletion of script-writable storage does not apply to Home Screen web apps, which "have their own counter of days of use" ([WebKit 2020](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)). A separate counter is not an exemption, however, and none of the sources confirms that Home Screen apps are fully protected. Since **iOS 26, every site added to the Home Screen opens as a web app by default** ([heise](https://heise.de/-10749652)). A client who logs in through Safari and also through her Home Screen icon therefore has two separate local stores, which makes the server the only reliable source of truth.

The offline UX rules are simple and testable. Do not block the interface with full-screen loaders. Queue writes and show that the item was **saved and will sync**, distinct from the online state. Show when data was last updated. Disable only the features that need the network. Announce connection changes with colour, text *and* an icon, since grey alone reads as disabled ([web.dev offline UX](https://web.dev/articles/offline-ux-design-guidelines)). The source does not cover how to present sync conflicts. Web push on iOS requires **16.4+, a Home Screen install, `display: standalone` and a permission request triggered by a user gesture** ([WebKit Web Push](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)). Safari has no `beforeinstallprompt`, so install UI must be gated on that event on Android and shown as instructions on iOS only when not already standalone ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeinstallprompt_event)). Serving the HTML network-first fits the app's boot-time build check better than cache-first, which can strand devices on an old build. That recommendation is an inference; no caching-strategy source was retrieved.

## Clients trust a portal that asks late, asks little, and shows who sees what

Reviews of category leaders identify reliability as the deciding UX feature. Vagaro's most common complaint is crashes that interrupt business. GlossGenius reviewers report outages that stopped clients booking, and "updates [that] often disrupted their workflow". Automated reminders are the most praised feature ([Capterra Vagaro](https://capterra.com/p/153752/Vagaro/reviews/); [GetApp GlossGenius](https://www.getapp.ca/reviews/2034787/glossgenius)). The evidence on reminders supports making them default-on: a meta-analysis found digital reminders cut no-shows by about **25% (15% vs 21%)**, with several reminders beating one ([PubMed 27798006](https://pubmed.ncbi.nlm.nih.gov/27798006/)). Jane's approach is the reference for intake: forms are sent automatically at booking, scoped by service, and kept in the portal next to the appointment ([Jane intake forms](https://www.jane.app/features/intake-forms)).

Permission requests work best when they explain themselves. NN/g found users **12% more likely to grant access when given a reason**. Ask in context (tap camera, then ask), frame the reason around the user's benefit, provide value before asking for anything non-essential, and after a denial deep-link to the exact setting ([NN/g permission requests](https://www.nngroup.com/articles/permission-requests/)). A USENIX study of 473 participants found the explanation mattered more than the timing ([Elbitar et al.](https://usenix.org/conference/usenixsecurity21/presentation/elbitar)). Forcing account creation has a measured cost: **19% of US shoppers abandoned an order over it** ([Baymard](https://baymard.com/blog/current-state-of-checkout-ux)). The magic link should be the account. Magic links suit infrequent, low-to-medium-risk users, with links typically **single-use and valid 5–15 minutes** ([AppMaster](https://appmaster.io/blog/passwordless-magic-links-ux-security-checklist); [LoginRadius](https://www.loginradius.com/glossary/magic-link)). Those are vendor sources, and vendor claims of support-ticket reductions lack independent evidence ([Baytech](https://baytechconsulting.com/blog/magic-links-ux-security-and-growth-impacts-for-saas-platforms-2025)).

For intake forms, **field count matters more than step count**. The average checkout asks for 11.3 fields when about 8 would do ([Baymard](https://baymard.com/blog/checkout-flow-average-form-fields)). NHS and GOV.UK recommend starting with **one question per page**, offering "I'm not sure" where it is a valid answer, and giving each page a back link that preserves answers ([NHS question pages](https://service-manual.nhs.uk/design-system/patterns/question-pages); [GOV.UK](https://www.gov.uk/service-manual/design/form-structure)). The Scottish design system cautions that this multiplies screens, so closely related questions can share a page ([Scottish design system](https://designsystem.gov.scot/patterns/question-page)). In a survey of 205 women aged 65 and over, the most wanted portal feature was **adjustable text size (47%)**. The top barriers were technical difficulty (50%) and **privacy (45%)** ([PMC9277451](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC9277451/)).

Privacy carries legal weight as well as usability weight. Holland & Knight (August 2026) writes that the FTC Act, the Health Breach Notification Rule and Washington's MHMDA apply to aesthetic providers **"regardless of whether they are classified as HIPAA-covered entities"**. FTC pixel settlements ran from **$100,000 to $7.8M** in 2023–2024. MHMDA requires separate opt-ins for collecting and for sharing health data, plus a response to deletion requests **within 45 days**. Nonessential tags should be blocked on "treatment, intake, booking, photo gallery, and patient portal pages" ([Holland & Knight](https://www.hklaw.com/en/insights/publications/2026/08/the-pixel-problem-advertising-triggers-health-data-obligations)). Using client photos in marketing requires specific, revocable written authorization, not a blanket consent ([RxPhoto](https://rxphoto.com/resources/blog/hipaa-photography-rules)); that source is a vendor blog written from a HIPAA perspective. No source in this research gives session-timeout values for non-HIPAA wellness apps, and none confirms from HHS or the FTC directly whether a cash-only esthetician is a covered entity. Legal review should settle both.

## Conclusion

The most useful thing an automated audit of SlickChart can do is not to chase the Lighthouse score. It is to codify the handful of states in which a provider or client is misled: an empty list during sync, an edit silently lost offline, an Undo toast that disappears with the only path back, a pixel firing on an intake page. Those rules (E1–E3, D1–D2, O1–O2, TR1) are where WCAG, NN/g, web.dev and current enforcement all point the same way. They are also the rules that generic accessibility scanners like axe never check, so they need custom Playwright scripts with mocked `/api/**` latency, failure and offline conditions. The pixel-level rules (T1, C1, Z1–Z3, SA1–SA2, F2) are cheap to run and should gate every branch push in CI. Because the shipped JavaScript runs against new servers for days, these sweeps should run in light and dark, at 320, 390 and 412 px widths, and under reduced motion every time.

Two things remain genuinely uncertain and should not be hard-coded as facts: iOS performance cannot be measured with INP or LoAF, and Apple has never documented the 16 px auto-zoom rule. Treat the first as a manual check on a real device each release. Enforce the second anyway, because it costs one CSS line and the practitioner evidence is unanimous. Where the platforms ask for more than WCAG (44–48 px targets, 7:1 small text in dark mode, 17 px body text), a solo provider working one-handed between treatments is exactly the user those stricter figures were written for.
